# Integration audit (Phase 1)
**Portal (kvbdtc-batch64):** Node/Express + TypeScript + Prisma/Postgres, JWT auth, ~215 models, 80 route files. Existing precedents reused: Moodle SSO/webhooks (idempotency), `card-gateway.ts` (HMAC over raw bytes, `express.raw` on the path), `AuditLog`. No existing VBL integration, event ledger, or webhook-retry system. `Enrollment` is keyed on **Unit**, not Course. Nothing in the base app ever set `Enrollment.status="withdrawn"` (added: `POST /api/registry/enrollments/:id/withdraw`).
**Lab (virtual-business-lab):** stdlib Python, SQLite, HMAC session tokens, RBAC, append-only audit, hash-chained evidence. **No enrolment concept, no frontend, and the FastAPI adapter has never been run.** Competency-based outcomes only (no percentage). Decided attempts are DB-locked.
**Conflicts found / decisions:** identity — Lab had its own users (now mapped, never duplicated); "grade" model mismatch (see Architecture); the zips were a *batch snapshot* of the portal (batch 64), not necessarily its full history.
**Bugs found in *this integration's own earlier code* by real tests (all fixed):** failed attempts never advanced the retry backoff clock; a FAILED event was acknowledged as a duplicate on redelivery (silent permanent loss — both systems); a permission string (`institution.manage`) that didn't exist in the Lab's RBAC; HMAC verification over re-serialised JSON.
**Security risks remaining:** shared-secret (not asymmetric) SSO; secrets in the DB are now AES-256-GCM encrypted (batch 66) but the key sits in the process environment (prefer a KMS-sourced key); the rate limiter is now Postgres-backed; no SSRF guard on `VBL_INTEGRATION_URL` (admin-set).
