# Operations runbook (batch 73)

Compact and factual: it describes what the repo does today. Where something is **not** in place it says so. Fill the **[ ]** fields for your institution.

## 1. Setup (dev and first install) — KOPS-021/022
1. Run `bash scripts/setup-env.sh` to create private `.env` files and generate database, JWT, webhook, and integration-encryption secrets. Set `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` (at least 8 characters; 14+ recommended), and the real `FRONTEND_ORIGIN` in the root `.env` before Compose.
2. `docker compose up -d --build` — services: `db` (Postgres 16, volume `pgdata`), `backend` (volume `uploads`), `frontend` (nginx, `HTTP_PORT`, default 8080). The backend entrypoint applies checked-in Prisma migrations and runs the idempotent seed before starting.
3. Check `docker compose ps`, then `curl http://localhost:8080/api/ready` (200 means API and database are ready). Configure TLS in front of nginx before exposing the portal publicly.
- Moodle is an optional external integration; this Compose stack does not start a Moodle server. Configure its URL, tokens, and webhook secret in the root `.env` after Moodle has been provisioned.
- Without Docker: `cd backend && npm ci && npx prisma generate && npm run build && npm start`; `cd frontend && npm ci && npm run build`. Backend unit tests: `npm test`. PostgreSQL-backed tests require an isolated database whose name contains `test` and `TEST_DATABASE_URL`; run `npm run test:all` from `backend/`.

## 2. Environment variables — KOPS-027
Documented in `.env.compose.example` and `backend/.env.example`. Compose requires `POSTGRES_PASSWORD`, `JWT_SECRET`, `FRONTEND_ORIGIN`, `SEED_ADMIN_EMAIL`, and `SEED_ADMIN_PASSWORD`; `HTTP_PORT` defaults to 8080. `INTEGRATION_SECRET_ENCRYPTION_KEY` is generated by the setup script and must be backed up separately from the database. Moodle, payments, AI, and other providers are optional and require institution-owned credentials. Other settings include `ANALYTICS_PSEUDONYM_SECRET`, `REMINDER_SCHEDULER_ENABLED`, `SESSION_TTL_MINUTES`, `INTEGRATION_SCHEDULER_ENABLED`, `OUTBOUND_ALLOW_HOSTS`, and `INSIGHTS_ROLES_<AREA>`.

## 3. Backup and restore — KOPS-026, KDR-002..005/007
**Not automated in this repo.** Two things hold data: the Postgres volume `pgdata` and the `uploads` volume.
- Database backup: `docker compose exec -T db pg_dump -U kvbdtc -Fc kvbdtc > kvbdtc-$(date +%F).dump`
- Uploads backup: `docker run --rm -v <project>_uploads:/u -v $PWD:/b alpine tar czf /b/uploads-$(date +%F).tgz -C /u .`
- Restore DB into an empty database: `docker compose exec -T db pg_restore -U kvbdtc -d kvbdtc --clean --if-exists < file.dump`; restore uploads by the reverse `tar xzf`.
- Schedule the two backup commands from the host (cron) and copy files off the server. Test a restore into a scratch stack at least once a term and record the result in §8.
- Integrity check: `pg_restore --list file.dump` must succeed; restored stack must pass `scripts/smoke.sh`.
- After a restore, integration events (Virtual Business Lab, Moodle) may need replaying: check Insights → Monitoring for backlog and dead letters.

## 5. Troubleshooting — KOPS-025 / KOBS-020
| Symptom | Check |
|---|---|
| Site down | `docker compose ps`; `curl :8080/api/health` (process) vs `/api/ready` (503 = database unreachable) |
| Everyone gets 401 | `JWT_SECRET` changed or missing; users must sign in again |
| Users locked out | Failed-login lockout is DB-backed (account + IP); clears with time; see Insights → Security |
| No emails/SMS | Email/SMS delivery is not implemented; Insights → Monitoring shows them as unsent |
| Lab (VBL) data not arriving | Insights → Monitoring: backlog / dead letters; Insights → Jobs for failed runs |
| Scheduled jobs silent | `REMINDER_SCHEDULER_ENABLED` / `INTEGRATION_SCHEDULER_ENABLED` must be `true` on exactly one instance |
| Fee figures look one minute old | finance report is cached 60 s |
| Library search source errors | outbound-URL guard blocks private addresses; add trusted internal hosts to `OUTBOUND_ALLOW_HOSTS` |

## 6. Deploy, rollback, migrations — KOPS-005/007/009, KDR-006
- Deploy: take a DB backup → deploy the reviewed source → `docker compose up -d --build` → confirm `docker compose ps` and `curl http://localhost:8080/api/ready`. The backend entrypoint runs `prisma migrate deploy` before seed and startup.
- Do not use `prisma db push` in production. For an existing database previously managed with `db push`, review and baseline migration history before deploying this migration-managed version.
- Rollback: redeploy the previous build only when its code is compatible with the applied migrations; migrations are not automatically rolled back. If data was damaged, restore the backup from §3.
- Staging: use a second `.env` and `HTTP_PORT` with `docker compose -p staging`. There is no separate staging config in the repo.
- TLS: terminate HTTPS in front of nginx (reverse proxy / load balancer).
